# 原 EXE 逆向与安卓移植计划

制定日期：2026-11-08。状态：实施计划，以下阶段不代表已经完成。

执行入口：已于 2026-11-08 新建独立工作区 `hamsterball_reverse`，开始第一阶段；见 [执行记录](../../hamsterball_reverse/docs/STAGE1_STATUS.md)。静态核查确认 Level1／BEGINNERRACE 对应内部 `Board (Warm-Up)`；内部 `Board (Beginner)` 实际对应 Cascade，后续以资源和调用链确定关卡身份。

## 目标与依据

通过逆向原 EXE 恢复游戏逻辑，把同一份 C++ 核心移植到 Android ARM64，尽量保留原版关卡、运动、碰撞、镜头、机关、声音与赛事规则。首个交付里程碑是 **Beginner 第一关完整还原**；通过验证后，再扩展至全部 15 条赛道及完整游戏流程。

基准为 4.2 安装包内 `original/hamsterball/hamsterball.exe`，SHA-256：

`047d6613005513e1cafc607f83b1520973828e77babbdaa52846723060a94b58`

研究依据见 [可行性报告](../research/FEASIBILITY.md)。安装包版本与游戏版本分别记录，不能把安装包的“4.2”直接当成游戏程序版本。

现有 Java/OpenGL 安卓预览保留作资源查看与平台接入参考。其猜测物理、120 Hz 时间步和镜头公式不作为还原基准。每项逆向结论标注“已验证／推测／未知”，反编译伪代码须经行为验证后进入核心。

## 阶段 1：建立原版基准与逆向工具链

工作：

- 固定 EXE、资源、配置、存档与测试起始状态，所有记录绑定哈希及工具版本。
- 盘点反编译器、C++ 编译器、Android NDK；建立 Ghidra 或同等工具的分析数据库，校正函数边界、调用约定与虚表。
- 建立可实际运行原版的 Windows 环境。实体机、虚拟机或兼容层按实际 D3D8、输入和音频运行结果选择，不预设兼容性已经解决。
- 为第一关录制静止、加速、松手、转向、撞墙、边缘跌落、复位、终点等基准片段；核实第一关涉及的动态对象与事件。
- 建立固定输入重放；定位逻辑时间步、坐标、速度、相机与随机状态的采集方法，先测量原版本身的重复性。

交付：原版运行说明、逆向数据库及导出脚本、第一关输入／视频／可采集状态、对象与字段置信度表。

验收：能从明确初始状态重复运行同一输入，并说明尚存在的随机性与采样限制。原版完整环境未就绪时可继续隔离函数研究，但不进行整关保真验收。

## 阶段 2：攻克真实碰撞，决定核心路线是否成立

这是首个技术决策门槛。

- 从运动求解候选 `0x463200`、构造 `0x4627d0`、初始化 `0x4630e0` 出发，追踪实际碰撞对象、虚调用、三角形数据与接触结果结构。
- 恢复扫掠检测、接触点／法线、滑动或反弹、容差、迭代与半径缩放的真实含义；查明构造默认值是否被调用者覆盖。
- 扩展原机器码探针，构造单三角形、平地、斜坡、墙面、边缘、薄平台、高速位移案例，覆盖实际发生接触的分支。
- 将经验证的数学和碰撞函数恢复为独立桌面 C++，建立“原机器码输出 vs C++ 输出”的差分程序。
- 检查 x87 中间精度、浮点存储点、运算顺序与 ARM64 舍入差异，保留必要的数值语义。

交付：首批 `native/core/` 函数、字段布局、原始输入输出样本、差分工具和碰撞验证报告。

验收：真实接触分支已执行，命中对象／三角形、接触状态及输出误差可解释。只有空场景位移一致不能通过。若无法稳定恢复，先缩小函数与场景定位原因，不用估算物理参数填补后宣称还原。

## 阶段 3：恢复第一关完整运动与状态

- 找到真实更新主链、时间单位、暂停和计时机制，明确物理更新是否固定步长及其与渲染的关系。
- 恢复键盘／鼠标／手柄到控制量的映射、灵敏度、加速度、重力、摩擦、速度约束及材料覆盖值。
- 恢复球体旋转、跌落／碎球／复位、终点与第一关相关对象的状态更新和事件顺序。
- 在同一初始状态、随机状态及输入下连续重放，逐逻辑步比较位置、速度、接触、事件和计时；改变渲染帧率检查逻辑是否符合原版行为。

交付：可重放第一关的桌面核心、状态追踪文件、差异定位报告。

验收：加速、停止、转弯、碰撞、跌落、复位和过关均有对照记录；持续运动没有未解释的轨迹分叉或事件时序差异。

## 阶段 4：恢复镜头、画面与音频

分析可与阶段 2、3 交错进行，最终验收依赖相同游戏状态。

- 从 `CAMERALOCUS`、`CAMERALOOKAT` 引用恢复路径插值、跟随、朝向和投影，而非根据视频手调近似镜头。
- 核实 D3D8 矩阵、坐标系、光照、雾、材质、透明、深度、阴影与绘制顺序；优先实现 GLES 后端，只有实际需求证明必要时才选择 Vulkan。
- 恢复仓鼠动画、球体转动、子模型位置、碎球和其他效果。
- 核实 BASS／MO3 音乐播放内容、音效触发时刻及音量／音高等参数，选择安卓可用音频方案并对照播放结果。

交付：原版相机更新、渲染与音频适配、相同状态截图和声音事件对照。

验收：相机位置／矩阵有数值证据，同分辨率画面对照可检查偏差，音乐与关键音效内容及触发时间符合基准。不能仅凭“整体看起来类似”通过。

## 阶段 5：同一核心落地 Android，交付第一关

- 以 CMake／NDK 编译同一份 C++ 核心到 ARM64，JNI 连接生命周期、文件、输入、音频和渲染。
- 用相同测试样本分别比较“原版 vs 桌面 C++”和“桌面 C++ vs Android ARM64”，避免两层误差相互掩盖。
- 触屏单独转换为原版控制量；保留标准输入重放通道，区分逻辑保真与手指操作体验。
- 处理后台切换、暂停恢复、音频焦点、资源释放、窗口尺寸和存档。
- 完成模拟器和安卓真机验证；选定测试设备后，以稳定 60 FPS 为初始性能目标，优化渲染时不擅改物理规则。

交付：第一关还原版调试 APK、可复现构建说明、真机记录、已知差异清单。

验收：第一关可完整游玩，关键重放通过，跨架构差异符合冻结后的标准，生命周期与性能问题有实测结果。当前预览 APK 不计作此里程碑。

## 阶段 6：扩展全部赛道与完整规则

- 建立“赛道—类—资源—机关—事件”覆盖矩阵，按依赖恢复机关；保持 Level7 = Wobbly、Level8 = Toob 的正确映射。
- 逐步验证桥梁、升降台、旋转部件、风车、锤、弹射器、敌人等；具体先后由依赖图与原版证据确定。
- 覆盖 Odd 的重力／尺寸机制、Neon 的光照／平台、Glass 的材料以及 Impossible 的齿轮／摆锤等特殊行为，逐项核实实际语义。
- 每种机关先做独立状态／接触测试，再做整关成功、失败与恢复重放。
- 恢复菜单、赛事时间池、难度、奖牌、镜像、解锁与存档；竞技场及多人规则放在单人赛事核心稳定后处理，移动端输入另行适配。

交付：全赛道可玩版本、机关实现和覆盖矩阵、逐关回归记录、完整游戏流程。

验收：15 条赛道分别有通关与失败恢复证据，赛事和存档流程可重现；“能加载关卡”不等于“已还原／可通关”。多人功能独立标明验证状态。

## 阶段 7：保真回归与移动端收尾

- 全量运行固定输入与机关回归，在多种刷新率、分辨率和选定真机上检查逻辑、画面及声音。
- 检查长时间运行、帧时间、内存、温度、后台恢复和触屏设置。
- 整理每项偏差的原因与影响，区分已验证、有限验证与未完成内容。

交付：候选 APK、构建与验证记录、最终差异报告。正式发布另行安排。

验收：约定测试集通过，剩余差异明确披露；没有证据时不宣称“100% 完全一致”。

## 验证标准草案

以下为待原版基准建立后确认的目标，不是当前已经达到的结果。先测量原版重复性，再冻结容差，后续不能为掩盖失败任意放宽。

| 层次 | 初始目标 |
| --- | --- |
| 简单数学函数 | 在相同浮点存储语义下逐位一致；复杂函数同时记录 ULP、绝对误差和分支差异 |
| 实际碰撞 | 命中对象／三角形与事件分支一致，接触与输出数值在明确容差内；边缘失配必须单独解释 |
| 连续轨迹 | 先以 60 秒重放、最大位置漂移不超过球半径的 1% 为目标；事件顺序和触发逻辑步一致 |
| 相机与视觉 | 比较相机数值、矩阵及同状态同分辨率截图；渲染后端差异单独登记 |
| 音频与流程 | 原内容、触发时间线、状态切换和赛事计时一致 |
| Android | 与桌面核心使用相同样本，另验触控、生命周期和真实设备性能 |

每份重放／样本记录 EXE 与资源哈希、配置、初始状态、随机状态、输入格式版本、时间步与计量单位。无法精确采集的字段明确留空并说明限制，不补造参照数据。

## 主要风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 原版 Windows 运行环境不稳定 | 先解决稳定基准；隔离函数可继续研究，但不替代整关验证 |
| 反编译结构或虚调用判断错误 | 保存原地址与字段偏移，用真实输入和原机器码检验 |
| 隐藏全局状态、计时或随机性 | 追踪调用链、初始化与状态快照，先确认重复性 |
| x87 与 ARM64 长期轨迹漂移 | 保守编译设置、核实舍入点，持续重放与边缘接触测试 |
| D3D8／音频后端产生差异 | 按状态与播放参数逐项映射，用截图／音频事件核验 |
| 全游戏工作量超出早期预估 | 第一关先验收，再按机关覆盖矩阵逐批扩展 |

## 文件组织与时间安排

目录随阶段实际需要建立；本计划不创建空脚手架：

```text
original/         原始文件与哈希，保持可核验
reference/        原版基准、输入、状态与视频
research/         反汇编、分析数据库、探针及结构注释
native/core/      经验证的跨平台游戏逻辑
native/platform/  平台接口
native/render/    渲染实现
tests/            原版／桌面／ARM64 差分与回归数据
android/          安卓入口及接入层，保留现有预览来源说明
docs/             计划、实现证据与差异报告
dist/             可交付构建
```

目前的少量函数探针不足以给完整游戏承诺可信工期。阶段 2 通过后评估第一关成本；阶段 5 通过且机关矩阵明确后，再评估全游戏。每阶段结束都提交可运行产物、原版证据、差异和剩余风险。
