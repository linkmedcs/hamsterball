# 原 EXE 逆向与安卓移植可行性研究

研究对象：幻想游戏 4.2 包内 `hamsterball.exe`，大小 1,478,656 字节。
SHA-256：`047d6613005513e1cafc607f83b1520973828e77babbdaa52846723060a94b58`。

## 判断

**技术上可行，值得继续做有明确验收条件的核心逻辑验证。当前证据支持“逐函数逆向并移植”，尚不能保证完整游戏可自动转换，也不能保证最终逐帧完全一致。**

最有价值的发现是：在 ARM64 Mac 上，已经将原 EXE 的少量 x86 机器码放进指令模拟器，成功执行运动相关对象的初始化、方向缩放辅助函数和运动求解器的无碰撞分支，全程没有加载 Windows 或调用 Windows API。这为后续建立“原版函数输出 vs 移植函数输出”的测试机制提供了实际可行的起点。

当前安卓预览使用重新编写的物理和镜头，不能作为原版行为基准。研究结果仅写入 `research/`，没有据此修改游戏运行逻辑。

## 已确认的证据

| 项目 | 实际结果 | 对移植的意义 |
| --- | --- | --- |
| 二进制类型 | x86 32 位 PE，入口 `0x4cb43e`，标准 `.text/.rdata/.data/.rsrc` | 能直接分析原生代码；不是可直接恢复源码的 .NET 程序 |
| 代码体积 | `.text` 有效大小 `0xdcb2a`，约 883 KiB | 相对现代游戏较小，但仍含引擎、库和运行时，不能按体积直接估算工期 |
| 可分析性 | 代码可直接反汇编，.text 熵约 6.572；未见常见压缩壳节名、解包入口或整体加密代码特征 | 暂未遇到先脱壳才能研究的障碍；这不是全面反保护审计 |
| 符号 | 调试目录为空，符号已剥离，未发现游戏源码/PDB 路径 | 原变量、结构体和函数名需要人工重建 |
| 代码组织 | 1,697 个不同直接调用目标，78 段连续代码指针候选区 | 存在较清晰的函数和虚函数表结构；这些数字不是准确函数/类总数 |
| 语义线索 | 关卡类名、`CAMERALOCUS`、`CAMERALOOKAT`、机关事件标签均有代码引用 | 可以从资源标记追踪到对应处理逻辑 |
| 资源 | 86 个 world、33 个 mesh、100 个 cache 已能完整读取；70 个 world 与 cache 的三角形数量一致 | 几何与资源提取已有基础，不必重新制作原关卡；计数一致不等于所有语义已还原 |
| 物理依赖 | 11 个静态导入 DLL 中没有独立物理引擎 DLL；存在可执行的内部运动求解代码 | 至少部分物理实现位于 EXE 内；不能仅凭导入表判断全部代码来源 |
| 原始代码探针 | 成功执行 5,088 条指令，覆盖 580 个不同指令地址，100 组方向缩放输入与 4 组空场景运动输入通过 | 已实际验证小范围原始函数可在 Windows 之外作为行为参照执行 |

Linker 主版本为 7，代码包含 x86 C++ 虚函数、异常处理和大量 x87 浮点操作，符合较早的 Visual C++ 原生程序特征。具体编译器版本尚未确认。

| --- | --- | --- |

| `0x41dab0` | Beginner 赛道构造候选，写入 `Board (Beginner)` 与 `0x4f89d8` 虚表 | 较高 |
| `0x428e50` | `Board (Dark)` 构造候选，即霓虹赛道相关类 | 较高 |
| `0x42a510` | `Board (Glass)` 构造候选 | 较高 |

| `0x419bb4` | `E:GRAVITY` 引用，位于 Odd 关卡事件处理候选范围 | 事件入口线索，尚未完整验证重力翻转 |

| `0x4630e0` | 初始化方向、半径候选、求解迭代数与多个系数 | 已读取真实字段；系数语义与关卡覆盖值尚未全部确认 |
| `0x4014b0` | 保存 scalar，并把 `+0xc8c` 的方向乘 scalar 写到 `+0xc98` | 100 组随机浮点输入逐项与恢复公式一致 |
| `0x463200` | 按半径缩放坐标、迭代调用碰撞对象、处理运动结果的求解函数 | 4 组无碰撞分支执行成功；地面/墙面碰撞分支尚未验证 |

`board-map.json` 记录 32 个 Board/RumbleBoard 命名实例的候选构造入口、名称赋值点和虚表线索。虚表切分为启发式结果，不能直接当成完整 C++ 类定义。

## 探针的证明范围

`probe_original.py` 只映射 PE 的节、测试堆和测试栈，从指定地址开始执行，在预设返回地址停止；它不调用 EXE 主入口，不提供 Windows API，也不启动原游戏。

构造探针得到的字段包括：迭代数 `3`、半径候选 `25`、方向 `(0,-1,0)`、若干系数 `0.555/1/1000`。这些只是对象初始化状态。**不能直接把它们全部命名为“原版摩擦/重力/速度”，更不能把初始化阶段算出的缩放方向当作实际游戏每帧重力。**还需要查调用点、全局初始化、关卡覆盖以及时间单位。

方向缩放函数可恢复为如下核心行为，其中偏移保留原对象布局：

```cpp
object.scalar_at_c64 = scalar;
object.vector_at_c98.x = float(object.direction_at_c8c.x * scalar);
object.vector_at_c98.y = float(object.direction_at_c8c.y * scalar);
object.vector_at_c98.z = float(object.direction_at_c8c.z * scalar);
```

此函数的 100 组输入输出一致，是逐函数移植方法的小型证明，不代表完整物理已被移植。空场景求解器的 4 个案例仅证明无障碍时输出等于起点加位移，尚未证明反弹、滑动、连续碰撞、穿隧处理和机关接触正确。

## 推荐实现方式

建议新建 C++/NDK 游戏核心，逐模块恢复原函数与状态机，安卓界面只承担生命周期、触屏和设备接入。现有 Java 原型保留作资源预览器，不再作为“原版还原”逻辑基础。

1. 先从 EXE 恢复数学类型、球体状态、时间步、输入归一化和运动求解。保存原函数地址、输入结构与输出样本。
2. 将恢复函数编译为桌面 C++，与隔离运行的原机器码做差分测试。先验证单函数，再验证连续几百帧状态。
3. 将同一份通过校验的 C++ 核心编译到 Android ARM64；通过 JNI 提供状态和输入。避免分别维护两套物理实现。
4. 平台层替换 Windows 的窗口、文件、计时和输入。渲染保留原 D3D8 的矩阵、材质状态与绘制顺序语义，重新实现 GLES/Vulkan 后端。
5. 用 Windows 原版完整运行建立画面、输入和状态基准，逐项比对相机、机关、音乐、菜单与赛事流程。

不建议把反编译伪 C 直接拼成项目，或试图把 x86 EXE 直接重新编译成 ARM64。反编译器能辅助分析，但对象布局、间接调用、内联代码、全局状态和平台接口仍需人工恢复。

## 平台接口与难点

| 原版依赖 | 移植处理 | 主要风险 |
| --- | --- | --- |
| Direct3D 8 | 恢复相机与渲染状态，映射到 GLES/Vulkan | 固定管线光照、材质透明、深度偏移、坐标与绘制顺序决定视觉差异 |
| DirectInput 8 / Win32 输入 | 保留原输入到加速度的映射，增加触屏适配 | 手指输入与鼠标增量/键盘状态不是同一种信号，需要明确映射规则 |
| BASS / DirectSound | 查明原音乐、采样和播放参数，采用可运行的安卓音频后端 | 原 Windows DLL 不能直接链接到 ARM64；MO3 播放内容与节拍不能凭重编码猜测 |
| Win32 文件、注册表、计时 | 平台封装 | 存档布局、默认配置、时间单位及暂停恢复需要保持逻辑 |
| 内部游戏对象与虚表 | 重建类和数据结构 | 动态平台、敌人、触发器和关卡派生逻辑分散在多个函数 |
| x87 浮点 | 先明确每处舍入与存储边界，再做 ARM64 对照 | x87 中间精度、ARM FMA、运算重排可能造成长期轨迹分叉 |

EXE 的制作人员字符串列出物理作者 `PAUL NETTLE` 和 `fluidstudios.com`。这可作为后续寻找公开算法资料的检索线索；本次没有联网核实其是否对应任何公开源码，不能据此假设引擎源码已经可得。

## 下一步应做的验证关卡

下一阶段应限于“第一关核心还原”，通过后再决定扩大到整个游戏：

1. 建立反编译数据库，标出真实函数边界、数学/碰撞结构与间接调用关系。
2. 接入原版三角形碰撞对象到隔离探针，测试平地、斜坡、墙边、台阶、悬崖及高速运动。当前还没有完成这一步。
3. 恢复真实输入映射、时间步和求解器参数，验证固定输入序列的坐标、速度、碰撞标志和复位点。
4. 恢复第一关 `CameraLocus` 的插值与相机更新，记录相同输入时的相机矩阵。
5. 获取可运行的 Windows 原版环境做全程序动态调试和对照录像。当前机器未发现 Wine 或完整反编译工具，本次未运行 Windows 原版。
6. 将经过差分测试的第一关核心接入 Android，再与桌面 C++ 输出比较。

验收应记录误差而不是凭“感觉差不多”：相同初始状态与输入下，比较每帧位置/速度、事件触发帧、计时、相机矩阵；明确容忍度，并观察连续轨迹是否累计漂移。对一关通过这些检查，才足以证明核心移植路线，而不只是资源加载路线。

## 尚不能承诺的内容

- 无法从这个已剥离符号的 EXE 一键恢复原项目、注释和原始类型名称。
- 尚未建立完整碰撞与真实关卡逻辑的差分测试，不能承诺 100% 行为一致。
- 全关卡、多人、菜单、存档和机关仍有相当规模的人工逆向工作；属于持续工程，不能按几次调参或解包工作估算。
- 当前没有完成 Windows 原版动态基准、正式反编译或 ARM64 原核心移植；本轮结论是“值得推进下一阶段验证”，不是“完整移植已证实完成”。

## 复现与文件

- `analyze_exe.py`：只读 PE 信息、静态导入与反汇编线索。
- `static-inventory.json`、`anchors.tsv`、`board-map.json`：机器可读结果。
- `hamsterball-4.2.asm`、`pe-headers.txt`：反汇编与 PE 头。
- `probe_original.py`、`original-probe-results.json`：原机器码隔离验证与全部样本。

静态研究：

```sh
python3 research/analyze_exe.py
```

隔离探针需要 Unicorn 2.1.4；本次研究库下载到 `/tmp/hamsterwheel-research-deps`，未安装到系统 Python：

```sh
PYTHONPATH=/tmp/hamsterwheel-research-deps python3 research/probe_original.py
```

本机执行探针需要允许指令模拟器使用原生执行能力；受限环境会在 Unicorn 初始化阶段触发 SIGILL。本次在获准的环境下执行成功。该脚本不用于运行任意未知入口；新增函数前必须先核实其调用约定与依赖。
